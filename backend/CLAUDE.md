# Backend — FastAPI

Python **3.14** · FastAPI · SQLAlchemy 2.1 async (asyncpg) · Alembic (async) · PostgreSQL · pytest · uv · ruff · mypy.
Despliegue: Cloud Run (`southamerica-east1`) + Cloud SQL vía Cloud SQL Python Connector.

Patrones de arquitectura con su porqué y el módulo de referencia (`app/modules/accounts`): `docs/arquitectura-backend.md`. **Léelo al crear un módulo, una capa o un patrón nuevo.**

> **Nota:** los comandos de abajo son la convención acordada. Los fija **KAN-17 [BE-01]**: si esa tarea (o una posterior) los cambia, **actualiza este archivo en la misma tarea**.

## Comandos (siempre desde `/backend`)
| Para | Comando |
|---|---|
| Instalar dependencias | `uv sync` (usa `uv add <paquete>` solo si el plan aprobado lo incluye) |
| Levantar la API en local | `uv run fastapi dev app/main.py` |
| Tests (todos) | `uv run pytest` |
| Tests de un archivo | `uv run pytest tests/api/test_spaces.py -q` |
| Lint | `uv run ruff check .` |
| Formato (verificar) | `uv run ruff format --check .` |
| Tipos | `uv run mypy .` |
| Nueva migración | `uv run alembic upgrade head` y luego `uv run alembic revision --autogenerate -m "<descripción>"` |
| Aplicar migraciones | `uv run alembic upgrade head` |
| Exportar OpenAPI | `uv run python -m app.export_openapi` → `backend/openapi.json` (opcional `-o <ruta>`; no levanta el servidor ni necesita BD) |
| Regenerar tipos TS (si cambió la API) | `cd ../frontend && npm run gen:api` → `frontend/src/lib/api/schema.d.ts` (el CI falla si difieren) |

La BD local y el emulador de Firebase Auth se levantan con `docker compose up -d` desde la raíz del repo.

## Convenciones de código
- **Capas:** `router → service → repository`. Services y repositories son **funciones async con `session` como primer parámetro** (no clases ni interfaces ABC). El service no conoce HTTP ni hace commit. El repository solo guarda consultas.
- **Entre módulos:** orden fijo `users/auth → currencies → spaces → accounts, categories → transactions → recurring, budgets, goals → dashboard`.
  - Un service solo llama services de módulos **anteriores**; los routers pueden combinar services de cualquier módulo.
  - De otro módulo solo se importan `service`, `schemas` y (desde la capa HTTP: routers y `dependencies.py`) `dependencies`, nunca `repository` ni `models`. Se intercambian schemas (`XRead`) o valores simples, nunca objetos ORM.
  - Si un caso de uso necesita un dato de un módulo posterior, el router lo trae y se lo pasa al service. Ejemplo ya hecho: el saldo de una cuenta vive en `transactions` (dueño de los entries), así que `accounts/router.py` pide `transactions_service.get_account_balances` y arma `AccountWithBalance` (`AccountRead` + `balance_minor`); `AccountRead` queda para el service y otros módulos.
  - Los `dependencies.py` son capa HTTP como los routers: pueden combinar `service`/`schemas` de cualquier módulo, y solo pueden importar `dependencies` de módulos de **nivel inferior** (`spaces.dependencies` usa `auth.dependencies`). Un `service.py` o `repository.py` no puede importar las `dependencies` de otro módulo.
  - Lo vigila `tests/unit/test_module_boundaries.py` (`ast`, sin BD): también exige que `service.py`/`repository.py` no llamen `commit()`/`rollback()` ni importen `HTTPException`/`Request`, y que `app/core` no importe módulos. Un módulo nuevo debe añadirse a `ORDER` en ese archivo o el test falla.
- **Multi-espacio:** toda función de repository recibe `space_id` y filtra por él. El borrado suave se filtra en una consulta base del repository, nunca en cada llamada (`transactions.repository._counted_entries`: espacio + `confirmed` + sin `deleted_at`, de donde parte toda consulta de saldos).
- **Mismo espacio garantizado por la BD:** una tabla que referencia filas de otras tablas del espacio (`entries` → transacción, cuenta, categoría) repite `space_id` y usa **FK compuestas** `(x_id, space_id) → (id, space_id)`, que exigen un `UNIQUE (id, space_id)` en la tabla destino (`accounts`, `categories`, `transactions`). Así la BD rechaza una fila que mezcle espacios aunque el service lo olvide; el service igual valida antes para dar un 422 con `loc`. Las tablas futuras con referencias (`recurring_templates`, `budgets`, `goal_allocations`) lo adoptan al crearse; un `category_id` NULL salta su FK (MATCH SIMPLE). En el modelo, un campo llamado `date` obliga a importar `import datetime as dt` y escribir `dt.date`: el atributo de clase pisaría el tipo `date`.
- **Regla que lee una fila y luego escribe algo que depende de ella** (crear o desarchivar una subcategoría exige la principal activa): se lee la fila con `SELECT ... FOR SHARE` (`with_for_update(read=True)`, `categories.repository.get_for_share`). Una FK solo toma `FOR KEY SHARE`, que no choca con el UPDATE que cambia ese estado (archivar). Quien cambia el estado actualiza **primero** esa fila y después sus dependientes (`archive_category`), así en READ COMMITTED uno espera al otro y el que va segundo ve lo que el primero confirmó. **Nunca** hagas UPDATE, en la misma transacción, de una fila que leíste con `FOR SHARE`: si dos transacciones tienen el SHARE de la misma fila y las dos intentan actualizarla, se bloquean entre sí (deadlock). Para leer y luego modificar la misma fila se lee con `FOR NO KEY UPDATE` (`categories.repository.get_for_update`, `with_for_update(key_share=True)`): es el lock que el propio UPDATE toma mientras no cambie columnas de una clave única referenciada por una FK, y no frena las FK de otras tablas (`FOR UPDATE` sí las frenaría); así dos archivados simultáneos de la misma categoría se serializan en vez de pisar el `archived_at`. Se prueba con el solapamiento forzado de `tests/db/test_category_archive_concurrency.py`.
  - **Saldos y cuentas:** toda operación que escribe movimientos (o cambia el saldo de una cuenta: crear, confirmar, restaurar, editar) lee las cuentas afectadas con `FOR SHARE` (`accounts.service.get_account_for_share`), en orden fijo por id, y no hace UPDATE de esas filas en la misma transacción. Las dos operaciones que deciden a partir del saldo, archivar y cuadrar, leen la cuenta con `FOR NO KEY UPDATE` en lugar de `FOR SHARE` (ver abajo). Archivar una cuenta (`POST .../accounts/{id}/archive`, KAN-67) lee la cuenta con `FOR NO KEY UPDATE` **y solo después** calcula el saldo (si se calculara antes del lock, un movimiento confirmado en medio dejaría una cuenta archivada con saldo). Esa regla vive en un solo lugar: `accounts.service.archive_account(session, space_id, account_id, *, balance_of)` toma el lock, recién entonces espera `balance_of()` (un callable async que trae el router desde `transactions.service.get_account_balance`, porque `accounts` no puede llamar a un módulo posterior), exige saldo 0 (`ConflictError` 409 `account_has_balance`) y archiva; el router no puede equivocar el orden. Archivar una archivada o desarchivar una activa no cambia nada (200); desarchivar no mira el saldo. Se prueba con el solapamiento forzado de `tests/db/test_account_archive_concurrency.py` (`tests/overlap.py`), en ambos órdenes y con doble archivado. **Cuadrar saldo** también decide a partir del saldo (escribe `real − saldo actual`), así que `transactions.service.reconcile_account` lee la cuenta con `FOR NO KEY UPDATE` (`accounts.service.get_account_for_update`, que devuelve un schema) y solo después el saldo: dos cuadres simultáneos (doble toque) se serializan y el segundo ve diferencia 0 en vez de escribir el ajuste completo otra vez, y un movimiento en vuelo se espera o espera al cuadre (con `FOR SHARE` el cuadre no esperaría a nadie y la cuenta podría quedar en el doble). El `FOR SHARE` que `create_transaction` pide después sobre la misma cuenta no espera ni causa deadlock: los locks de una misma transacción no chocan y `NO KEY UPDATE` es el más fuerte. Se prueba en `tests/db/test_account_reconcile_concurrency.py`. La categoría de un movimiento se lee sin lock: los movimientos viejos conservan categorías archivadas, así que no hay invariante que proteger. Se prueba de forma determinista, sin tiempos, con `NOWAIT` en `tests/db/test_transaction_account_lock.py`.
  - **Moneda del espacio (KAN-68):** `GET /currencies` (autenticado, 401 sin sesión) devuelve todas las filas de `currencies` (`code`, `exponent`) ordenadas por código. `PATCH /spaces/{id}` (`SpaceUpdate`, solo `currency`; cualquier otro campo da 422 `extra_forbidden`) cambia la moneda **solo mientras el espacio no tenga ninguna transacción** (de cualquier `status` y borradas incluidas: un monto guardado se lee con el exponente de la moneda de su espacio, así que cambiarla después reinterpretaría todos): 409 `space_has_transactions`; 422 `currency_unsupported` si no está en `currencies` (se valida antes del lock, así que gana al 409); la misma moneda que ya tiene da 200 sin cambios, aun con movimientos; `{}` da 200 sin UPDATE. La respuesta es `SpaceRead` (el mismo schema de `GET /spaces` y `GET /spaces/{id}`), que trae `currency_locked: bool` (true si el espacio tiene alguna transacción: la UI muestra la fila "Cambiar moneda" mientras sea false). Como `spaces` no puede llamar a `transactions`, se aplica el patrón de `archive_account`: `spaces.service.update_space(session, space_id, data, *, has_transactions)` recibe un callable async que trae el router (`transactions.service.space_has_transactions`, sin filtro de `status` ni `deleted_at`, a propósito: lo contrario de `_counted_entries`) y lo espera **después** de leer el espacio con `FOR UPDATE` (`spaces.repository.get_for_update`). Aquí hace falta `FOR UPDATE` y no `FOR NO KEY UPDATE`: el INSERT de cualquier transacción toma `FOR KEY SHARE` sobre su espacio por la FK `fk_transactions_space_id_spaces`, y solo `FOR UPDATE` choca con él; así un movimiento en vuelo hace esperar al cambio (que luego lo ve y da 409) y uno posterior espera al cambio (y se escribe en la moneda nueva), sin tocar `create_transaction`. Dos cambios simultáneos se serializan. Se prueba con `tests/db/test_space_currency_concurrency.py` (con `NO KEY UPDATE` los tests de solapamiento fallan por timeout). **`SpaceBase` y `SpaceRead`:** `SpaceBase` (id, name, type, currency, timezone) es lo que devuelve el service de `spaces` (a otros módulos y al router); `SpaceRead` = `SpaceBase` + `currency_locked` es la respuesta de la API, que arma el router con `_with_currency_locked` (una consulta `EXISTS` por espacio, servida por `ix_transactions_space_id`). El nombre `SpaceRead` se conserva para la API porque el frontend ya tipa con él (al revés que `AccountRead`/`AccountWithBalance`). **Cuando un módulo nuevo guarde montos del espacio** (`recurring_templates`, `budgets`, `goals`), `has_transactions` del router y `currency_locked` deben responder también por ellos, o el cambio de moneda los reinterpretaría.
- **Dinero:** `int` en Python, `BigInteger` en BD, siempre en la **unidad menor de la moneda** según ISO 4217 (valor × 10^exponente: USD/UYU/COP ×100, CLP/PYG ×1; no siempre centavos). Sin `float` ni `Decimal` en la BD. El exponente sale de la tabla `currencies` (módulo `currencies`), única fuente de las monedas soportadas: sumar una moneda es agregar una fila en una migración de datos, y `spaces.currency` es FK a ella. En los schemas, el tipo común `Amount` (`app/core/schemas.py`): int estricto, > 0, ≤ 2^53 − 1 (el límite seguro de JavaScript); `SignedAmount` es el mismo tope con signo y distinto de 0 (error `amount_zero`), solo para el ajuste, que es un delta del saldo; `Balance` es el mismo tope con signo y **admite 0**: un saldo como se lee, no un movimiento (`initial_balance_minor` de `AccountCreate` y `balance_minor` de `AccountReconcile`). Ambos llevan **el signo de `balance_minor`**: en una tarjeta, deuda = negativo (una deuda de 3.000 se manda como -300000). **Saldo inicial y cuadre:** `POST /spaces/{id}/accounts` con `initial_balance_minor` distinto de 0 crea la cuenta y, en la misma transacción, un ajuste por ese monto (lo compone el router de `accounts` con `transactions.service.create_adjustment`; omitido, null o 0 no escribe nada). `POST .../accounts/{id}/reconcile` con el saldo real (`transactions.service.reconcile_account`) escribe un ajuste por `real − saldo actual`, o nada si la diferencia es 0 (se serializa con otros cuadres, movimientos y archivados de la misma cuenta, ver "Saldos y cuentas"; 409 `account_archived` si la cuenta está archivada; 422 `balance_out_of_range` si la diferencia pasa el tope, porque `ck_entries_amount_range` daría un 500). El ajuste es `confirmed`, sin categoría ni descripción, y su fecha es el día local del espacio en el momento `now` que pasa el router (`create_adjustment` la calcula con `spaces.timezone`; es el único lugar que fecha ajustes). Las columnas se llaman `*_minor` (`amount_minor`), no `*_cents`. Los schemas de entrada validan el formato de la moneda con `CurrencyCode` (`app/modules/currencies/schemas.py`: 3 letras mayúsculas); que esté soportada lo decide `currencies` (service o FK). El signo lo pone el backend según el tipo (`build_entries`). **Saldo** (`balance_minor`): suma de los entries de transacciones `confirmed` sin `deleted_at`, con signo; el de una tarjeta es negativo cuando se debe. `GET /spaces/{id}/balance-summary` devuelve `available_minor` (banco + efectivo), `card_debt_minor` (el opuesto de la suma de las tarjetas: positivo = se debe, sin recortar) y `net_minor` (= disponible − deuda = suma de todos los saldos); incluye cuentas archivadas. `SUM(bigint)` es `numeric` en PostgreSQL: el repository lo convierte a `int`.
- **IDs:** UUIDv7 generados en Python (`default=uuid.uuid7`).
- **Schemas:** `XCreate` / `XUpdate` (PATCH con `exclude_unset`) / `XRead`. Las entradas heredan de `InputModel` (`extra="forbid"`) y las salidas de `ReadModel` (`from_attributes`), ambas en `app/core/schemas.py`. Crear transacción = unión discriminada por `type` (`TransactionCreate`: gasto, ingreso, transferencia, ajuste; `transactions.service.create_transaction` crea siempre `confirmed` y arma los entries con `build_entries`, una función pura con `match` + `assert_never`, probada en `tests/unit`). **`POST /spaces/{id}/transactions` (KAN-74)** recibe `MovementCreate` = gasto | ingreso | transferencia, **sin ajuste** (un `type: "adjustment"` da 422 `union_tag_invalid`): los ajustes los fecha y calcula el backend (`create_adjustment`, `reconcile_account`), nunca el cliente. Responde 201 con `TransactionRead` (el cliente manda montos positivos; el signo lo pone `build_entries`: un gasto en tarjeta sube la deuda, una transferencia banco→tarjeta la baja). **`loc` de los 422 de este POST:** siempre `["body", "<type>", "<campo>"]`. Pydantic lo hace solo en una unión discriminada (mete el tag en el `loc`) y el service lo imita (`_check_accounts`, `_check_category`), así un campo tiene un solo camino sea cual sea la regla que lo rechaza (`validationIssuesOf` del frontend solo quita el `body` inicial y une el resto con puntos, así que da `"<type>.<campo>"`, p. ej. `expense.category_id`: el formulario de movimientos (FE-20) debe quitar el tipo o registrar sus campos con ese prefijo); `tests/api/test_transactions.py` lo vigila. Una cuenta o categoría de otro espacio da 422 `account_not_found` / `category_not_found`, idéntico a un id inexistente (no filtra); el 404 `space_not_found` es solo para el espacio de la ruta.
  - **`Idempotency-Key` (KAN-93):** el mismo POST acepta el header opcional `Idempotency-Key` (un UUID que genera el cliente, de cualquier versión; si no es un UUID, 422 `uuid_parsing` con `loc ["header", "Idempotency-Key"]`). Sin el header todo es como antes. Con él, `transactions.service.create_movement(session, space_id, user_id, data, *, idempotency_key, now)` (el router pasa `now=datetime.now(UTC)`) deja **un solo movimiento por `(space_id, user_id, key)`**: el mismo usuario y espacio con la misma clave y el mismo cuerpo no crea nada y responde 201 con el mismo `TransactionRead` (relee la transacción por id: la ve como está ahora, también si se borró después, y no revalida); la misma clave con otro cuerpo da **409 `idempotency_key_reused`** (`ErrorResponse`, no se escribe ningún dato). Otro usuario o espacio con la misma clave no interfiere. **Un request que falla (4xx o 5xx) no consume la clave**: toda la transacción de BD se deshace, así que un reintento corregido puede usar la misma clave. Las claves vencen a las 24 h (`IDEMPOTENCY_KEY_TTL`, contadas desde `now`): una vencida se ignora y la reemplaza el nuevo reclamo, aunque su cuerpo fuera otro; **no hay purga** (queda para el cron del hito 2).
    - **Orden y concurrencia:** la clave se **reclama primero**, antes de bloquear ninguna cuenta, con un solo `INSERT ... ON CONFLICT (space_id, user_id, key) DO UPDATE ... WHERE created_at <= :vencidas RETURNING` (`repository.claim_idempotency_key`). Si devuelve fila, la clave es nuestra: se llama a `create_transaction` tal cual y se ata la clave al movimiento (`attach_idempotency_key`, un UPDATE de `transaction_id`), todo en la transacción del request. Si no devuelve nada, la clave está vigente: `SELECT`, hash distinto → 409, igual → relee y devuelve el movimiento. Dos requests con la misma clave se encuentran en ese INSERT: el segundo espera, sin ningún lock tomado mientras espera, a que el primero termine; si confirma, el segundo ve la clave; si deshace (un 422, por ejemplo), la clave nunca existió y el segundo sigue como dueño. Por eso el reintento secuencial y el simultáneo pasan por la misma rama y no hay ciclos con los `FOR SHARE` de las cuentas. Un duplicado en vuelo espera (milisegundos): no hay un 409 "en curso". **Tras un conflicto con una clave vigente no se escribe ningún dato, pero la fila queda bloqueada** (`FOR NO KEY UPDATE`: PostgreSQL bloquea la fila en conflicto antes de evaluar el `WHERE` del `DO UPDATE`, aunque sea falso) hasta el commit/rollback del request. Es inocuo: el reintento o el 409 solo leen y no toman ningún otro lock, así que no hay ciclos; el único efecto es que dos reintentos simultáneos de la misma clave van uno tras otro (verificado con `NOWAIT` en `tests/db/test_transaction_idempotency_concurrency.py`).
    - **Hash del cuerpo:** `idempotency.request_fingerprint` = sha256 del `model_dump(mode="json")` ya validado, con JSON canónico (claves ordenadas, sin espacios, UTF-8). No se compara el texto del request: el orden de los campos, las mayúsculas de un UUID, una descripción con espacios alrededor o `description` omitido frente a `null` dan la misma huella; cualquier diferencia real (tipo, monto, fecha, cuenta, categoría, descripción) es otro request. Un campo nuevo con default cambiaría la huella de un reintento que cruce un deploy dentro de las 24 h (un 409 falso, aceptado).
    - **Tabla `idempotency_keys`** (`transactions.models.IdempotencyKey`, migración `0007`): PK `(space_id, user_id, key)` (es el UNIQUE del `ON CONFLICT`), `request_hash` bytea de 32 bytes (CHECK), `transaction_id` **nullable** (NULL solo dentro del request que reclamó la clave, entre el reclamo y la creación; esa fila no está confirmada, así que toda fila confirmada tiene su movimiento; lo comprueba `tests/db/test_transaction_idempotency_concurrency.py` con commit real) y `created_at`. Dos FK compuestas con `ON DELETE CASCADE`: `(user_id, space_id) → space_members` (el usuario es miembro del espacio) y `(transaction_id, space_id) → transactions(id, space_id)` (mismo espacio). Se escribe solo con el `INSERT ... ON CONFLICT` y el UPDATE del repository, nunca con el unit of work del ORM. Se prueba en `tests/unit/test_idempotency_fingerprint.py`, `tests/services/test_transactions_idempotency_service.py`, `tests/api/test_transactions_idempotency.py` (+ `_concurrent`, dos POST con `asyncio.gather` sobre pool real), `tests/db/test_idempotency_keys_migration.py` y `tests/db/test_transaction_idempotency_concurrency.py` (solapamiento forzado: misma clave, otro cuerpo, el primero deshace, dos reclamos sobre una clave vencida (la rama `DO UPDATE`), el bloqueo de la fila con `NOWAIT` y los controles de que claves o usuarios distintos no se esperan).
  - **PATCH (`PatchModel`, `app/core/schemas.py`):** `XUpdate` hereda de `PatchModel` (que hereda de `InputModel`) y solo declara lo editable; un campo fijo como `type` queda fuera y da 422 `extra_forbidden`. Cada campo se declara `Tipo = unset()` (helper de `app/core/schemas.py`: devuelve `Any` a propósito, porque el plugin `pydantic.mypy` rechaza `Field(default=None)` en un campo no nullable) **sin** `| None`: omitido = no se toca, y un `null` explícito da 422 `null_not_allowed` con el `loc` del campo (lo comprueba `PatchModel` leyendo la anotación). Un campo que sí se puede vaciar se declara `Tipo | None = None` y acepta null. Así OpenAPI y los tipos TS dicen `name?: string`, no `string | null`; `tests/unit/test_patch_model.py` lo vigila para todas las subclases. **Un PATCH se lee solo con `model_dump(exclude_unset=True)`**, nunca con atributos sueltos: los defaults no se validan, así que un campo no enviado vale `None` aunque su tipo diga otra cosa. `{}` da 200 sin UPDATE. Una regla que depende de datos guardados (los días solo valen en una tarjeta) la valida el service con `InvalidFieldError` y el mismo código que el POST. En un `XCreate`, las reglas entre campos se validan por campo (`field_validator` con `info.data` y `validate_default=True`), no con un `model_validator`: así el `loc` marca el campo. **En un `PatchModel` nunca se usa `validate_default=True`** (el validador de null correría sobre el default `None` y omitir un campo daría 422 `null_not_allowed`): ahí una regla entre campos, o que dependa de datos guardados, va en el service (como los días).
- **Endpoints:** `response_model=XRead` devolviendo el objeto ORM, `status_code` explícito (201 al crear, 204 sin cuerpo) y `responses={404: {"model": ErrorResponse}}` con los errores posibles.
- **Tiempo:** momentos como `timestamptz` en UTC; la fecha de una transacción como `date` local del usuario. La zona horaria vive en `spaces.timezone`.
- **Nombres:** tablas en plural y snake_case; JSON en snake_case; URLs con guiones (`/recurring-templates`).
- **Rutas de espacio:** `/spaces/{space_id}/...` con `require_space_member` declarada en el `APIRouter` (`dependencies=[...]`), no endpoint por endpoint. No miembro → **404** (no revelar que existe).
- **Rutas sin `z` final:** Cloud Run reserva algunas rutas que terminan en `z` y recomienda evitarlas todas (su frontend responde con un 404 propio sin que la petición llegue a la app). La ruta de salud es `GET /health`; ninguna ruta de la API termina en `z`, sin excepciones. `tests/api/test_routing.py` falla si aparece una.
- **Acciones de negocio** como endpoints explícitos: `POST .../confirm`, `/skip`, `/cancel`, `/archive`.
- **Crear por intención:** el cliente manda "gasto de 1550 en Comida desde Itaú"; el backend arma los `entries`.
- **Editar** = rehacer los entries. **Borrar** = `deleted_at` (borrado suave).
- **Paginación por cursor**, orden `date desc, id desc`: cursor opaco (base64 de `date` + `id`), `limit` de 1 a 100, respuesta `Page[T]` (`items`, `next_cursor`; `app/core/schemas.py`, cada módulo la nombra: `MovementPage(Page[MovementListItem])`, para que OpenAPI y TS no generen `Page_X_`). Filtros como modelo de query `Annotated[Filtros, Query()]` con `extra="forbid"`. Nunca ordenar por un texto del cliente.
  - **Leer movimientos (KAN-79):** tres GET en el router de `transactions`. **`GET /spaces/{id}/transactions`** devuelve `MovementPage` (`MovementListItem` = `MovementRead` + `balance_after_minor`); **`GET .../transactions/summary`** devuelve `TransactionSummaryRead`; **`GET .../transactions/{transaction_id}`** devuelve `MovementRead` (404 `transaction_not_found` si está borrado, es de otro espacio o no existe: el mismo cuerpo). `summary` se declara **antes** que `{transaction_id}` (si no, `summary` se leería como UUID).
  - **Filtros** (`TransactionFilters`: `month`, `type`, `account_id`, `category_id`, `q`; `TransactionListFilters` suma `limit` y `cursor`; el resumen no acepta paginación: 422 `extra_forbidden`). Todos opcionales y combinados. `month` (`YYYY-MM`, años 1900-2199) es `date >= 1.º del mes AND date < 1.º del siguiente` sobre `transactions.date`, que ya es la fecha local del espacio: **no hay conversión de zona**; qué mes es "el actual" lo decide el front con `spaces.timezone`, la API no tiene mes por defecto. `type` omitido = todos (los ajustes salen). `account_id` = algún entry en esa cuenta (en una transferencia, origen o destino). `category_id` = la categoría y, si es principal, sus subcategorías (archivadas incluidas): `categories.service.category_ids_with_subcategories` resuelve los ids y el listado filtra `Entry.category_id IN (...)`. **Una cuenta o categoría ajena o inexistente da 200 con lista vacía y resumen en ceros** (no 422: no filtra nada y la UI muestra "sin resultados"). `q` (1 a 100 caracteres, sin espacios en los extremos) busca en la descripción sin distinguir mayúsculas ni acentos: `unaccent(description) ILIKE unaccent(patrón)` con `ESCAPE '\'` y `\`, `%`, `_` escapados en Python (`_escape_like`), así que el texto del usuario es literal. Necesita la extensión `unaccent` (migración `0008`); sin índice propio (la acota el espacio y, normalmente, el mes).
  - **Cursor y orden:** `cursor.py` (`encode_cursor`/`decode_cursor`, base64 url-safe sin relleno de `"YYYY-MM-DD|<uuid>"`); un cursor que no se decodifica da 422 `cursor_invalid` con `loc ["query", "cursor"]` (lo lanza el `field_validator` de `TransactionListFilters`; el service lo vuelve a decodificar). Keyset `(date, id) < (d, i)` con `LIMIT limit + 1`: el par es único, así que las páginas no repiten ni saltan filas aunque muchas compartan fecha, y una cantidad múltiplo del límite no deja una página vacía al final. Lo sirve el índice parcial `ix_transactions_space_id_date_id_active` (comprobado con `EXPLAIN`, sin ordenar). Un cursor no da autoridad: solo una posición, y toda consulta filtra por `space_id`.
  - **Qué lista:** la base `_active` (`repository`) es espacio + sin `deleted_at`, **en cualquier `status`** (pendientes y saltados salen con su `status`; no suman en totales ni en saldos). Cada ítem trae la cuenta y la categoría con nombre e ícono: `list_movements` pide **2 consultas pequeñas por página** (`accounts.service.list_accounts` y `categories.service.list_categories`, archivadas incluidas) y arma los ítems con diccionarios (`movement_view.build_movement`), así que las sentencias no dependen del tamaño de la página (lo comprueba un test que cuenta sentencias). `amount_minor` lleva signo por tipo: gasto negativo, ingreso positivo, ajuste con su signo, **transferencia sin signo** (el front compara `from_account`/`to_account` con la cuenta filtrada). `account` sale en gasto, ingreso y ajuste; `from_account`/`to_account` solo en transferencia; `category` solo en gasto e ingreso (`parent` = la principal de una subcategoría).
  - **Resumen** (`GET .../transactions/summary`): los mismos filtros que el listado, `type` incluido (las cifras cuadran con la tabla). `count` = filas que mostraría el listado (cualquier tipo y status, sin borrados): la m de "Mostrando n de m". `income_minor` y `expense_minor` (ambos positivos) suman solo `confirmed` de tipo `income`/`expense`, sobre entries (así los filtros de cuenta y categoría acotan lo sumado, también si un día se divide una compra); ajustes, transferencias, pendientes, saltados y borrados no suman. `remaining_minor` = ingresos − gastos ("Te quedan"; puede ser negativo).
  - **Saldo tras el movimiento** (`balance_after_minor`, solo con `account_id`; null en otro caso y en pendientes/saltados): `repository.balances_after` suma en orden `(date, id)` **todo el historial que cuenta** de esa cuenta (`_counted_entries`), agregado primero por transacción y con `SUM(...) OVER (ORDER BY date, id ROWS UNBOUNDED PRECEDING)`; el filtro por los ids de la página va en una consulta exterior (el WHERE corre antes de las ventanas). **No depende de los demás filtros**: un movimiento que un filtro oculta igual movió el saldo. Lleva el signo de `balance_minor` (tarjeta con deuda = negativo). Coste: una pasada por los entries de la cuenta por página (medido: ~230 ms con 60 000 entries en una sola cuenta; una cuenta personal tiene decenas de miles como mucho). Si hiciera falta, la alternativa es el saldo actual menos la suma de lo más nuevo que la página. Un movimiento fechado en el pasado cambia el saldo de los posteriores.
- **Errores** (`app/core/errors.py`): el service lanza `AppError`: `NotFoundError(code, detail)` 404, `ConflictError` 409, `UnauthenticatedError` 401, `ForbiddenError` 403 (p. ej. `origin_not_allowed`) e `InvalidFieldError(loc, code, msg)` 422 con el formato de validación de FastAPI (`loc` es una tupla o lista, p. ej. `("body", "category_id")`; un `str` suelto da `TypeError`). Lanza siempre una subclase: un `AppError` directo (o una subclase sin su propio status 4xx) es un bug y responde como cualquier error no previsto (500 genérico + traza). Respuesta `{"detail": "<inglés>", "code": "<snake_case estable>"}` (`ErrorResponse`); el frontend traduce `code`. No uses `HTTPException` en código nuevo (si aparece, o un 404/405 del router, se convierte al mismo formato con `code` = frase HTTP: `not_found`, `method_not_allowed`). Un error no previsto da 500 `{"detail": "Internal server error", "code": "internal_error"}` con `X-Request-ID`: lo captura `RequestIdMiddleware`, que loguea **una** traza y **no relanza**. Nunca filtrar trazas ni SQL al cliente.
- **Logs** (`app/core/logging.py`): una línea JSON por evento en stdout, con `severity` (no `level`; es lo que lee Cloud Logging), `message`, `logger`, `timestamp` y `request_id`. Con `GOOGLE_CLOUD_PROJECT` y el header `X-Cloud-Trace-Context` (lo añade Cloud Run) suman `logging.googleapis.com/trace`. Los campos de `extra=` nunca pisan los reservados. El `X-Request-ID` entrante se reutiliza si cumple `[A-Za-z0-9._-]{1,64}`; si no, se genera. Los logs de Uvicorn salen por el mismo formateador desde el `lifespan`; las líneas de arranque anteriores al lifespan ("Started server process"...) siguen en texto hasta que el despliegue use `--log-config`. Nunca loguear tokens, cookies ni datos personales completos.
- **Async:** relaciones con `selectinload` explícito y `lazy="raise"` en toda `relationship()`; nunca lazy loading. Una sesión no se comparte entre tareas (`asyncio.gather` con la misma sesión, no). Librerías síncronas (`firebase-admin`, `google-auth`) con `await asyncio.to_thread(...)`.
- **Cloud Run:** sin `BackgroundTasks` para trabajo importante (la CPU se limita tras responder), sin estado en memoria entre requests y sin caché de respuestas.
- **Skill `fastapi`** (`.claude/skills/fastapi/`, la oficial de FastAPI 0.142.2): síguela en lo que no choque con este archivo. Diferencias conocidas, donde gana el proyecto: SQLAlchemy 2.1 async con modelos ORM separados de los schemas (no SQLModel), mypy (no ty), *path operations* `async` porque el acceso a datos es async de punta a punta (asyncpg), y rutas **sin barra final**: con `prefix`, la colección se declara con `""` y no con `"/"` como en los ejemplos de la skill (que generan `/items/`). La app usa `redirect_slashes=False`: una barra final da 404, no 307 (`tests/api/test_routing.py` vigila que ninguna ruta termine en `/`). Al subir de versión FastAPI, actualiza la copia de la skill desde el paquete instalado.

## Configuración
- Variables vía `pydantic-settings`. La lista completa y comentada está en `backend/.env.example` (nunca leas `.env`).
- `FIREBASE_AUTH_EMULATOR_HOST` solo existe en local: si está definida en staging/prod con **cualquier** valor distinto de vacío (solo espacios incluidos), la app debe negarse a arrancar (la regla vive en `Settings`; nada más la repite). `firebase-admin` solo mira `os.environ` y trata todo valor no vacío como emulador (y entonces no comprueba la firma). Con `ENV=local` vale `localhost:9099` por defecto y vacía (o solo espacios) la desactiva. `Settings` puede venir de `backend/.env`: `create_firebase_auth` hace que `os.environ` coincida siempre con `Settings`, copiando el valor allí o borrando la variable si `Settings` no la tiene.
- **`ENV` y Cloud Run:** si falta `ENV`, la app asume `local`. Para que un olvido en el despliegue no abra los docs, el emulador ni cookies sin `Secure`, el `lifespan` se niega a arrancar con `Settings.ENV == "local"` si existe `K_SERVICE` (Cloud Run lo define siempre; se lee de `os.environ`, nunca del `.env`: `running_on_cloud_run()` en `app/core/config.py`). En staging/prod, `ENV` va en el entorno del servicio. La regla está en el `lifespan` (junto a la de los docs, que también compara el entorno del proceso con `Settings`) y no en `Settings`, para que construir `Settings` (tests, alembic, export) no dependa de dónde corre el proceso.
- `FIREBASE_PROJECT_ID`: proyecto para el que se emiten los ID tokens. Con `ENV=local` vale `demo-finance-local` (el del emulador: debe coincidir con `FIREBASE_EMULATOR_PROJECT_ID` de la raíz y con el del frontend); obligatoria en staging/prod.
- `ALLOWED_ORIGINS`: orígenes del frontend (lista separada por comas, solo `esquema://host[:puerto]`, sin barra final) que pueden crear o cerrar sesión. Con `ENV=local` vale `http://localhost:3000`; obligatoria en staging/prod. Un valor mal formado (o con un puerto inválido) impide arrancar. Se normalizan a minúsculas y sin el puerto por defecto (`:443` en https, `:80` en http), porque los navegadores no lo envían en `Origin`.
- `GOOGLE_CLOUD_PROJECT` (opcional): id del proyecto de GCP para el campo trace de los logs. Cloud Run no lo expone al contenedor, hay que configurarlo en el servicio; sin él solo se pierde la correlación (aviso `gcp_project_not_set` al arrancar fuera de local).
- **Docs de la API:** `/docs`, `/redoc` y `/openapi.json` solo existen con `ENV=local` (o sin definir). `create_app()` lo decide con `docs_enabled()`, que lee `os.environ` y **no** construye `Settings` (el export no puede depender de variables); cualquier otro valor las oculta. El `lifespan` se niega a arrancar si `Settings.ENV` no es `local` y los docs están activos (p. ej. `ENV` solo en un `.env`): en staging/prod, define `ENV` en el entorno del proceso.
- **Base de datos** (`app/core/db.py`):
  - `DATABASE_URL` (driver `postgresql+asyncpg://`): con `ENV=local` tiene valor por defecto; en staging/prod es obligatoria, salvo que exista `INSTANCE_CONNECTION_NAME`.
  - Con `INSTANCE_CONNECTION_NAME` se usa el Cloud SQL Python Connector (`DB_USER`, `DB_PASSWORD`, `DB_NAME` obligatorias; `DB_IP_TYPE` por defecto `PUBLIC`; vacías o solo espacios cuentan como no definidas) y `DATABASE_URL` se ignora.
  - Los engines usan `hide_parameters=True`: los errores de SQL no incluyen los valores de los parámetros.
  - Pool pequeño (2–5): `DB_POOL_SIZE=2` + `DB_MAX_OVERFLOW=3`, `DB_POOL_TIMEOUT=30`.
- **Sesión de usuario** (`app/modules/auth/`): `POST /auth/session` (`id_token`, `timezone`) y `DELETE /auth/session` (204). Ambos exigen `Origin` en `ALLOWED_ORIGINS` (`require_allowed_origin`, declarada en el `APIRouter`; ausente o distinto → 403 `origin_not_allowed`). El POST verifica el ID token con `firebase-admin` (`auth_time` de menos de 5 min, si no 401 `recent_sign_in_required`; token inválido o sin `auth_time` 401 `invalid_id_token`; cuenta sin email 401 `email_required`), crea la session cookie de 14 días y, en la misma transacción, hace el upsert del usuario y crea "Mi espacio" (UYU, la zona recibida) si no existe y, solo si lo creó, le siembra las 34 categorías predefinidas (`categories.service.seed_default_categories`; idempotente). Firebase se llama antes de tocar la BD (el pool es de 2–5 conexiones).
  - **Cookie:** `session` sin `Secure` con `ENV=local`; `__Host-session` con `Secure` en cualquier otro entorno. Siempre `HttpOnly`, `SameSite=Lax`, `Path=/` y sin `Domain`. El nombre y `Secure` salen de `Settings.session_cookie_name` / `session_cookie_secure`; leer, poner y borrar la cookie pasa por `auth/cookies.py` (`read_session_cookie`, `set_session_cookie`, `clear_session_cookie`; un `__Host-` solo se borra con los mismos atributos).
  - **Cerrar sesión (`DELETE /auth/session`):** cierra en **todos** los dispositivos del usuario. Verifica la cookie (`verify_session_cookie(check_revoked=True)`; el uid sale solo de una cookie verificada y vigente) y llama a `revoke_refresh_tokens(uid)` (`auth.service.end_session`). Siempre 204 y siempre borra la cookie: sin cookie, con una inválida/vencida/ya revocada o con la cuenta borrada no revoca nada (si la cuenta se borra justo entre la verificación y la revocación, `FirebaseAuth.revoke_refresh_tokens` devuelve `False` y el resultado es `no_session`, sin log `session_revoked`); si Firebase falla (en la verificación o al revocar) tampoco falla el logout, para que el usuario nunca quede atrapado, pero loguea un ERROR `session_revocation_failed` (`firebase_error` = clase del error, `firebase_uid` si ya se conocía, para poder revocar a mano; nunca la cookie ni el mensaje de Firebase). `end_session` devuelve `revoked` / `no_session` / `revocation_failed`: cambiar la política (p. ej. un 502 con la cookie borrada) es cambiar solo el router. Es la única excepción a "otro fallo de Firebase = 500" y por eso `end_session` captura `Exception` (el service no puede importar `firebase_admin`). El endpoint no usa `DbSession`: no ocupa conexión del pool. Firebase compara el `iat` de la cookie con el momento de la revocación **en segundos enteros**: una cookie emitida en el mismo segundo que la revocación no queda revocada (irrelevante en la práctica).
  - **`current_user` y `require_space_member`:** `CurrentUser` (`auth/dependencies.py`) lee la cookie, la verifica con `verify_session_cookie(check_revoked=True)` (una llamada a Firebase por request, sin caché) y busca el usuario por `firebase_uid`. Sin cookie → 401 `not_authenticated`; cookie inválida, expirada, revocada, cuenta deshabilitada o borrada, o usuario sin fila en la BD → 401 `invalid_session`. Firebase inaccesible → 500 genérico. `require_space_member` (`spaces/dependencies.py`) no miembro o espacio inexistente → 404 `space_not_found` (el mismo cuerpo, nunca 403). `SpaceMember` es el alias para leer el rol en un endpoint. `tests/api/test_routing.py` comprueba, para toda operación `/spaces/{space_id}/...`, que sin cookie responde 401 `not_authenticated` y que con sesión válida de un usuario sin espacios responde 404 `space_not_found` (una ruta que solo use `CurrentUser` falla); no sustituye al test de IDOR de cada endpoint.
  - **Frontera con Firebase:** `auth/firebase.py` es el único archivo que importa `firebase_admin` (sin tipos: override de mypy en `pyproject.toml`; import perezoso para que importar la app no lo cargue). `FirebaseAuth` es un `Protocol`; `app.state.firebase` se crea y se cierra en el `lifespan`, y `get_firebase_auth` (la dependencia que los tests sobreescriben) lo lee. Los errores de token son 401; cualquier otro fallo de Firebase sale como el 500 genérico (salvo en el logout, ver arriba).
  - **Composición:** `users` y `auth` son nivel 0, `spaces` nivel 2 y `categories` nivel 3, así que el router de `auth` compone `auth.service`, `users.service`, `spaces.service` y `categories.service` (los services no se llaman entre sí; `spaces` no puede llamar a `categories`, por eso el router trae el id del espacio con `spaces.service.get_personal_space_id` y se lo pasa a la siembra).
  - `display_name` solo se escribe al crear el usuario; los logins siguientes solo refrescan el `email`; la zona horaria de un espacio existente nunca cambia.
  - `Timezone` (`app/core/schemas.py`) valida contra la lista de `tzdata` (no contra `zoneinfo.available_timezones()`, que depende del sistema); el error es `timezone_invalid`.
- **Sesión y transacción por request:** `DbSession` (`from app.core.db import DbSession`). La dependencia usa `scope="function"`: hace **commit si el endpoint termina bien y rollback si falla, antes de enviar la respuesta**. **Para revertir hay que lanzar** un `AppError`: devolver una respuesta 4xx sin lanzar hace commit. Los services **nunca** llaman `commit()` ni `rollback()`; usan `flush()` si necesitan el id o detectar una restricción (un `IntegrityError` esperable → `ConflictError`). Así, una operación que cruza módulos es una sola transacción. Fuera de HTTP (scripts), commit explícito.
  - `get_sessionmaker` es la dependencia de la que sale la fábrica de sesiones; los tests de API la sobreescriben.
  - Restricción de FastAPI: una dependencia con `yield` y scope por defecto (`request`) no puede depender de una `scope="function"`. Cualquier dependencia **con `yield`** que use `DbSession` debe declararse también con `scope="function"`; las sin `yield` (p. ej. un futuro `get_current_user`) no tienen esa restricción.
- **Modelos ORM:** heredan de `app.core.db.Base`. Toda restricción tiene nombre predecible (convención `pk_`, `fk_`, `uq_`, `ck_`, `ix_`); cada `CheckConstraint` **debe llevar `name=`**. Al crear los modelos de un módulo, importa su `models.py` en `migrations/env.py` para que autogenerate los vea.

## Contrato OpenAPI
- `backend/openapi.json` está **versionado** y se genera con `uv run python -m app.export_openapi`: claves ordenadas, indentación de 2 espacios, UTF-8 y un único `\n` final, así que dos corridas dan los mismos bytes. El frontend genera sus tipos a partir de él.
- Si un cambio toca la API (rutas, schemas, respuestas), **regenéralo en el mismo cambio**. `tests/unit/test_export_openapi.py` falla si el archivo versionado no coincide con la app.
- **Importar la app no debe construir `Settings` ni el engine** (viven en el `lifespan`, que el export no ejecuta): el export tiene que funcionar sin BD ni variables de entorno. No llames a `get_settings()` ni crees engines a nivel de módulo en routers, models o schemas.

- **Tests de services y API: savepoint por test.** La BD de test se migra una vez por sesión de pytest y cada test corre en una transacción que se revierte al final (`join_transaction_mode="create_savepoint"`), así que los `commit()` no dejan datos. Fixtures: `migrated_test_database` (sesión; `alembic upgrade head` sobre `finance_test`; si la BD quedó en una revisión que no existe en la rama, falla con los comandos para recrearla), `db_connection`, `session_factory`, `session` (services) y `api_client` (sobreescribe `get_sessionmaker`, así corre el commit/rollback real de `get_session`; sin requests concurrentes: comparten conexión). `scratch_database_url` queda para los tests de `tests/db` que migran o prueban el engine; los demás (también en `tests/db`, p. ej. `test_savepoint_fixtures.py`) pueden usar `session`.
- **Concurrencia real** (`tests/db/test_first_login_concurrency.py`): el savepoint comparte una conexión y no muestra carreras; para eso, un engine por actor sobre `scratch_database_url` y el solapamiento forzado (la transacción A no confirma hasta que una tercera conexión, en AUTOCOMMIT, ve en `pg_stat_activity` a B esperando un lock), sin `sleep` fijos.
- El `lifespan` escribe `FIREBASE_AUTH_EMULATOR_HOST` en `os.environ`: el fixture autouse `_isolated_settings` lo deja registrado en `monkeypatch` para que no se filtre entre tests (y borra `K_SERVICE`). Un test que llame a `create_firebase_auth` sin ese fixture debe hacer lo mismo.
- `alembic.command.*` llama `asyncio.run` internamente: desde un test async, invócalo con `await asyncio.to_thread(...)`.
- **Tests con subproceso:** por defecto, `cwd` vacío (`tmp_path`, sin `.env`) y `env["PYTHONPATH"] = str(BACKEND_DIR)`: importa el `app/` real y reutiliza su bytecode (ver `test_connector.py`). El fixture `isolated_backend` (copia de `app/`, `migrations/` y `alembic.ini`, **con** `__pycache__`) solo se usa si el subproceso escribe junto al código (la ruta por defecto de `openapi.json`) o necesita `app/` y `alembic.ini` en el `cwd` (`prepend_sys_path`); en ese caso no pongas `PYTHONPATH`, o el subproceso tocaría el árbol real. Timeout `SUBPROCESS_TIMEOUT_S = 180` (red de seguridad en máquinas cargadas), definido en cada archivo.
- Cada test crea sus datos con funciones async de ayuda (`await make_space(session, ...)`), sin librerías de factories; nada depende del orden de ejecución.
- Las funciones puras (armado de entries, cursor) se prueban en `tests/unit` sin BD.
- Los movimientos pendientes, saltados o borrados no tienen ruta de creación todavía: los tests los crean con `tests.transactions_helpers.insert_transaction` (ORM directo, sin validar); el camino real va por `create_transaction` (`POST /spaces/{id}/transactions`).
- Prioridad alta: reglas de negocio (transferencias suman cero, saldo ignora pendientes y borrados, idempotencia del cron) y API (contratos, 422, 401, **IDOR**).
- Nombres que describen comportamiento: `test_non_member_gets_404_on_space_detail`.

## Migraciones
- Revisadas a mano después del autogenerate; con `downgrade` funcional.
- Antes del autogenerate, `uv run alembic upgrade head` sobre la BD local `finance`: autogenerate compara contra ella y falla ("Target database is not up to date") si no está en la última revisión. Después, `uv run alembic check` confirma que no quedan cambios sin migrar.
- Nunca editar una migración que ya está en `main`.
- Revision IDs secuenciales de 4 dígitos (`0001`, `0002`…): `uv run alembic revision --autogenerate --rev-id 0002 -m "<descripción>"`. Su `down_revision` apunta a la anterior (`"0001"`).
- Se aplican como paso separado (Cloud Run Job), **nunca** al arrancar la app.
- `env.py` usa la misma config y el mismo `Database` que la API (Connector incluido). `alembic upgrade head --sql` (modo offline) solo funciona con `DATABASE_URL`.
- La `0005` (transacciones y entries) añade `UNIQUE (id, space_id)` a `accounts` y `categories` **antes** de crear las FK compuestas que apuntan a ellos, y el downgrade los quita al final: el autogenerate los pone en el orden contrario y hay que reordenarlos a mano.
- La `0006` añade `ix_transactions_space_id`, un índice completo sobre `transactions.space_id`: el único otro con `space_id` es el parcial del listado (`WHERE deleted_at IS NULL`), que no sirve para saber si el espacio tiene alguna transacción borrada (`space_has_transactions`, que se pregunta con el espacio bloqueado).
- La `0007` crea `idempotency_keys` (PK compuesta, dos FK compuestas con CASCADE y `transaction_id` nullable a propósito; ver "`Idempotency-Key`"). Sin índices extra: la PK sirve a todas las consultas; la purga por `created_at` traerá su índice con el job que la ejecute. Su downgrade solo borra la tabla.
- La `0008` (a mano, no autogenerada) hace `CREATE EXTENSION IF NOT EXISTS unaccent` para la búsqueda del listado (`DROP EXTENSION IF EXISTS` al bajar). Es una extensión "trusted" (PostgreSQL 13+): la crea el dueño de la BD, sin superusuario; Cloud SQL la trae. **Antes del primer despliegue a staging hay que comprobar que el usuario del job de migraciones puede crearla.** `unaccent()` es STABLE, no IMMUTABLE: un índice sobre ella (trigram) necesitaría un envoltorio IMMUTABLE. En local, `uv run alembic upgrade head` sobre `finance` la instala.
- Las revisiones generadas se formatean solas con ruff (hook en `alembic.ini`). La primera (`0001`) crea `currencies` con su semilla; las monedas nuevas entran como migración de datos.
- La `0004` (categorías) también siembra los espacios existentes leyendo `spaces`, con una copia congelada de la lista predefinida dentro de la migración: no se puede renderizar con `alembic upgrade head --sql` (lanza un error claro). Una migración de datos no importa código de `app`, para que un cambio posterior no altere lo que hizo.
