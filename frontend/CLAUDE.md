# Frontend — Next.js

Next.js (App Router) · TypeScript **strict** · React Server Components · Tailwind CSS v4 · shadcn/ui con Base UI · Phosphor · TanStack Query · react-hook-form + zod · Firebase Auth (cliente) · openapi-typescript + openapi-fetch · vitest + Testing Library · Playwright (E2E, _pendiente_).
Despliegue: Vercel (funciones en `gru1`). Diseño **web responsive, escritorio primero**: las pantallas se diseñan para escritorio (1280 y 1440 px) y cada una tiene su versión de celular en el lienzo (mínimo garantizado 360 px). La barra lateral ancha aparece desde 1024 px (`docs/diseno.md` D15 y D17). En el código, Tailwind se escribe como siempre: la base es el celular y `lg:` el escritorio. Interfaz en **español**.

**Diseño y librerías de UI:** [`docs/diseno.md`](docs/diseno.md) — decisiones aprobadas (estilos, componentes, tokens, datos, formularios, modo oscuro, viewport) y checklist para empezar una pantalla. Léelo antes de crear o cambiar cualquier pantalla o componente.

## Versiones
Node **24** (`.nvmrc`, `engines`), Next.js **16**, React 19, TypeScript **5.9** y ESLint **9**. TypeScript se queda en 5.9 porque `openapi-typescript` (FE-02) pide `^5.x` y `typescript-eslint` solo llega a `<6.1` (TS 7 no está soportado); ESLint no pasa de 9 porque `eslint-config-next` 16 se rompe con ESLint 10 (`eslint-plugin-react`). Súbelos cuando esos paquetes lo soporten. Next, React y `eslint-config-next` van con versión exacta: cámbialos juntos. `recharts` (3.10.1, KAN-102) y `react-is` (19.3.0, peer de recharts: va con la versión de React) también van exactas: el `chart.tsx` de shadcn se escribió para una versión concreta de recharts. Vitest 5 usa Vite 8: el alias `@/` se resuelve con `resolve.tsconfigPaths` (no hace falta `vite-tsconfig-paths`).

## Comandos (siempre desde `/frontend`)
| Para | Comando |
|---|---|
| Instalar dependencias | `npm ci` (usa `npm install <paquete>` solo si el plan aprobado lo incluye) |
| Variables de entorno (una vez) | `cp .env.example .env.local` (sin ellas `dev` y `build` fallan). Si ya tenías un `.env.local`, añade `SESSION_COOKIE_NAME=session` (KAN-28) |
| Levantar en local | `npm run dev` → http://localhost:3000 |
| Catálogo de componentes (solo `next dev`) | http://localhost:3000/catalog: no existe en `build` ni en producción (ver `docs/diseno.md` D4) |
| Lint | `npm run lint` (`eslint .`; Next 16 ya no trae `next lint` ni lintea en el build) |
| Tipos | `npm run typecheck` (`tsc --noEmit`) |
| Formato (verificar / aplicar) | `npm run format:check` / `npm run format` (Prettier; no toca los `*.md`) |
| Build | `npm run build` (su `prebuild` borra `.next/dev` para que los tipos de rutas del modo dev, que incluyen `/catalog`, no rompan el build) |
| Regenerar tipos de la API | `npm run gen:api` (lee `../backend/openapi.json` y escribe `src/lib/api/schema.d.ts`; idempotente) |
| Tests (lógica y componentes) | `npm test` (vitest, una pasada) · `npm run test:watch` |
| E2E | `npx playwright test` _(pendiente: se instala con la primera sub-tarea de E2E; proyectos "Escritorio" Chromium a 1280 px (el principal), "iPhone" WebKit y "Pixel" Chromium a 360 px, y comparar la salida de `Intl` de Node con la de WebKit y Chromium; ver `docs/diseno.md` §4)_ |

`lint`, `typecheck`, `format:check` y `test` no necesitan variables de entorno; `dev`, `build` y `start` sí. `build` no necesita red: las fuentes están versionadas en `src/app/fonts/` y se cargan con `next/font/local` (KAN-42; ESLint prohíbe `next/font/google`).

En local, el backend corre en `http://localhost:8000` y el emulador de Firebase Auth en `localhost:9099` (`docker compose up -d` desde la raíz).

## Convenciones
- **API:** solo vía `lib/api/server.ts` o `lib/api/browser.ts`, tipados con `schema.d.ts`. Nunca `fetch` suelto al backend ni tipos de respuesta escritos a mano.
  - Servidor: `const api = await getServerApi();` (una vez por render) y `await api.GET("/ruta")`. Lee los headers de la petición, así que la ruta pasa a ser dinámica. No usa caché (`cache: "no-store"`).
  - Navegador: `browserApi` solo dentro del `queryFn` / `mutationFn` de TanStack Query (nunca en efectos sueltos). Su `baseUrl` es relativa, así que en Node falla con `Failed to parse URL`: en Server Components usa `getServerApi()`.
  - Las llamadas devuelven `{ data, error, response }`, ya tipados con `schema.d.ts`: no los redeclares a mano.
  - **Datos con TanStack Query** (D2): las funciones de datos viven en `lib/core/data/<recurso>.ts` y **reciben un `ApiClient`** (`lib/core/data/api-client.ts`), no importan un cliente. Exportan `xxxQueryOptions(api)` con la query key (`["spaces"]`, `["spaces", id]`…) y un `queryFn` que envuelve la llamada con `unwrap`: `queryFn: () => unwrap(api.GET("/spaces"))`. `unwrap` devuelve `data` o lanza `ApiError { status, body }` siempre que la respuesta no sea OK, también si viene sin cuerpo (un 404 o 502 vacío: `body` es `undefined`); en un 422, `body` es el detalle de FastAPI para mapear a campos. Un string de fecha-hora (`formatInstant`) debe traer `Z` o `±hh:mm`. El servidor y el cliente usan la misma función: el servidor con `getServerApi()`, el cliente con `browserApi`.
  - Tras una mutación, invalida las queries afectadas (`queryClient.invalidateQueries`).
- **Contrato:** si `openapi.json` cambió, corre `npm run gen:api`. El check `api-types` del CI falla si los tipos generados no coinciden. En tareas de backend que cambian la API, lo hace backend-dev en el mismo PR.
  - Un cambio del contrato que rompa lo que usa el frontend se ve en `npm run typecheck`. `lib/api/contract.check.ts` lo garantiza para `/health` y el cableado de los clientes (sus `@ts-expect-error` fallan si el cliente deja de rechazar llamadas erróneas).
  - Los endpoints reales se tipan al usarlos en la app; no hay que registrarlos en ningún sitio.
- **Rewrite:** `/api/:path*` → `${BACKEND_URL}/:path*` en `next.config.ts` (lo mantiene frontend; quita el prefijo `/api`). Funciona igual en local y en Vercel.
  - `BACKEND_URL` se lee con `serverSchema.parse(process.env)` (el schema puro, no `serverEnv`, que lleva `server-only`) y se fija al hacer `dev`/`build`: cambiarla exige reiniciar o volver a construir.
  - No crees rutas en `src/app/api/`: el sistema de archivos tiene prioridad sobre el rewrite y taparía el endpoint del backend.
  - Define las rutas del backend sin barra final: una redirección 307 de FastAPI apuntaría al backend y sacaría al navegador del origen.
- **`Referrer-Policy` y CSP (KAN-61):** la API key web de Firebase de staging está restringida por referrer (ver `infra/RECURSOS.md`). Hoy el sitio no define `Referrer-Policy` y rige la del navegador (`strict-origin-when-cross-origin`, que manda el origen). No pongas `no-referrer` ni una CSP que bloquee `identitytoolkit.googleapis.com`, `securetoken.googleapis.com` o el `authDomain`: el login dejaría de funcionar en staging y ningún check del CI lo detectaría. Si hace falta cambiarlas, coordínalo con infra.
- **Next.js 16:** la protección de rutas va en `proxy.ts` (antes `middleware.ts`, ya deprecado). Ante dudas de APIs, la documentación de la versión instalada está en `node_modules/next/dist/docs/`.
  - **Rutas privadas (KAN-27):** el proxy corre en Node y usa `serverEnv` (el layer del proxy admite `server-only`; verificado con `next build` y `next start`). Sin cookie de sesión (o vacía) → 307 a `/login` sin query y con `Cache-Control: no-store`. Solo comprueba que la cookie exista, con `pickCookie`, igual que `getServerApi()`; si es válida lo dice el backend. Una ruta nueva es privada sin tocar nada; una pública se añade a `PUBLIC_PATHS` (comparación exacta o por segmento: `/catalogo` no es `/catalog`). `/login` **no** redirige a `/` aunque haya cookie: una vencida o revocada haría un bucle (`/` → 401 → `/login` → `/`) y un Server Component no puede borrarla. `/catalog` pasa porque `docs/diseno.md` D4 lo exige; en producción no existe y da 404.
  - **Matcher:** debe ser una constante (Next la analiza al compilar). Excluye `/api` (el rewrite al backend: login y logout pasan por ahí y un 401 debe llegar como 401), `/_next/static`, `/_next/image` y los estáticos de `public/` en sus dos sitios: la raíz (`[^/]+\.(png|svg|ico|webmanifest)`, un solo segmento) y `brand/` (un nivel, `png` y `svg`). No excluye cualquier ruta que acabe en `.png`: una ruta dinámica futura como `/spaces/abc.png` debe pasar por el proxy. **Regla:** un estático nuevo va en la raíz de `public/` o en `public/brand/`; otra carpeta (o otra extensión) exige ampliar el matcher, y `proxy.test.ts` (recorre `public/`) falla hasta que se haga.
- **Server vs. client:** Server Components por defecto; `"use client"` solo donde haga falta interactividad o Firebase.
  - **Prefetch + hidratación:** en el Server Component, `const queryClient = new QueryClient()` (uno por request, nunca a nivel de módulo: son datos de usuario), `await queryClient.prefetchQuery(xxxQueryOptions(await getServerApi()))` y `<HydrationBoundary state={dehydrate(queryClient)}>` alrededor del componente cliente que hace `useQuery(xxxQueryOptions(browserApi))`. El `QueryClientProvider` ya está en `components/providers.tsx` (montado en `layout.tsx`).
  - **Core** (`lib/core/`): TypeScript puro compartible con la futura app nativa. ESLint le prohíbe importar `next/*`, `react-dom`, `server-only`, `lib/api/server`, `lib/api/browser` y `lib/env/*`; solo `import type` de `@/lib/api/schema`. Sin puertos "por si acaso".
- **Sesión:** el login con Firebase entrega un ID token → `POST /api/auth/session` → el backend responde con la cookie HttpOnly. El frontend **no guarda tokens**. Logout = `DELETE /api/auth/session`.
  - **Logout** (`components/use-logout.ts`, KAN-27; desde KAN-41 está en el menú de la cuenta, `components/user-menu.tsx`: el avatar del encabezado de `AppShell` bajo 1024 px y, desde FE-15, la fila de la cuenta abajo en la barra lateral desde 1024 px; `AppShell` dibuja los dos y toda pantalla con sesión lo tiene, en todos los anchos): `useLogout()` es una `useMutation` con `deleteSession(browserApi)`. Lo llama `UserMenu` (cada una de sus dos presentaciones tiene el suyo; solo una se ve) y no el ítem del menú, porque el ítem se desmonta al cerrarse el menú y `busy` debe sobrevivir a un Escape. El ítem (`closeOnClick={false}`) queda en el menú con spinner, `aria-busy` y `aria-disabled`; el disparador (el avatar o el botón de tres puntos) también lleva `aria-busy`. El backend responde siempre 204 (borra la cookie y revoca las sesiones en Firebase, en todos los dispositivos); solo falla con un 403 `origin_not_allowed` o un error de red: un toast en español (`describeApiError`), sin navegar, y se puede volver a pulsar. En éxito: `markSessionEnded()`, `queryClient.clear()` y `window.location.replace("/login")`. **Carga completa a propósito, no `router.replace`:** con una navegación del cliente, "atrás" restaura la página desde el Router Cache de Next ("reused during browser back/forward navigation") sin pasar por el servidor ni por el proxy y muestra los datos del usuario que se fue; la carga completa descarta ese caché y la memoria de JS (el `QueryClient` tiene datos del usuario), y `replace` saca `/` del historial.
  - **"Atrás" tras el logout, en capas:** (1) carga completa y `replace`; (2) las páginas dinámicas (toda la que llama a `getServerApi()`) salen con `Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate` (lo pone Next; verificado con `curl` sobre `next start`), así que ni la caché HTTP ni, en Chrome y Firefox, el bfcache las guardan; (3) donde el navegador igual restaure una página de su caché atrás/adelante (`pageshow` con `persisted`), `BfcacheGuard` la recarga (el proxy la manda a `/login`) y `markSessionEnded()` puso `data-session-ended` en `<html>`, que `globals.css` usa para ocultar el `body` mientras tanto. La capa 3 no se puede probar con jsdom ni Playwright, y en local el origen solo es `localhost`, así que se prueba en staging: KAN-30 (17/10/2026) probó el "atrás" a mano en un Pixel 10 (Chrome) y un iPhone 17 Pro (Safari, también con el gesto de "atrás"): tras "Cerrar sesión", no mostró datos del usuario. Con varias pantallas privadas en el historial sigue _pendiente_ (QA-06, KAN-85).
  - **Flujo del login** (`app/login/_components/login-form.tsx`, una sola `useMutation`): `signInForIdToken` → `createSession(browserApi, { id_token, timezone: Intl.DateTimeFormat().resolvedOptions().timeZone })` → `signOutQuietly()` (en un `finally`: también si el canje falla) → `router.replace("/")`. La zona del dispositivo se manda solo aquí: es la del espacio personal que crea el primer login.
  - **`lib/firebase.ts`:** `initializeAuth(app, { persistence: inMemoryPersistence, popupRedirectResolver: browserPopupRedirectResolver })` y `signInWithPopup(auth, new GoogleAuthProvider())`; nunca `signInWithRedirect` (falla en móvil). Con `getAuth()` el SDK guardaría el token en IndexedDB. Con el resolver y la persistencia en memoria no queda ningún token en el navegador: el resolver solo lee `sessionStorage` por si hay un redirect pendiente, y solo los flujos `...WithRedirect` escriben ahí (verificado leyendo `@firebase/auth` 12.x: `_setPendingRedirectStatus` y `prepareUserForRedirect`); el popup nunca.
  - **Popup y Safari/iOS:** `window.open` tras una espera de red se bloquea (`auth/popup-blocked`). Antes de abrir el popup el SDK carga el iframe del `authDomain`, y solo lo precarga al crear el auth si ya tiene el resolver y estás en móvil, Safari o iOS. Por eso el resolver va en `initializeAuth` y `LoginForm` llama a `prepareFirebaseAuth()` en un `useEffect` al montarse (lo prepara antes del primer toque; es idempotente y no abre nada). El SDK sigue siendo perezoso: no se inicializa al importar el módulo ni en el servidor (la página también se renderiza allí). `firebase/auth` se importa de forma estática, no con `import()`, por lo mismo. Un toque en los primeros instantes, antes de que cargue el iframe, aún podría bloquearse. KAN-30 (17/10/2026) lo probó en staging en un Pixel 10 (Chrome) y un iPhone 17 Pro (Safari): el popup de Google abrió al primer toque, sin `auth/popup-blocked`.
  - **Emulador:** si existe `NEXT_PUBLIC_FIREBASE_AUTH_EMULATOR_HOST`, `connectAuthEmulator` (sin banner). En local, abre la app en `http://localhost:3000` (no `127.0.0.1` ni la IP de la LAN): el backend solo acepta ese origen en `ALLOWED_ORIGINS` y respondería 403 `origin_not_allowed`.
  - **Comprobar la cookie a mano:** inicia sesión en `/login` y, en `/catalog`, pulsa "Probar GET /me" (200 con tu email = la cookie HttpOnly llegó y viaja en las llamadas de `browserApi`).
- **Server Components** llaman directo a `BACKEND_URL` y **reenvían solo la cookie de sesión** de la petición entrante (KAN-28): `getServerApi()` lee la cabecera `Cookie` en bruto (`(await headers()).get("cookie")`) y `pickCookie` deja únicamente `SESSION_COOKIE_NAME=<valor>`, con el valor exactamente como llegó; no usa `cookies()` porque eso re-codifica los valores. Las demás cookies del navegador (tema, analítica, la de Vercel…) no salen de Next. Si no hay cookie de sesión no se manda cabecera `Cookie` y el backend responde 401. Un `Set-Cookie` del backend no se propaga desde un Server Component (no puede escribir cookies).
  - **Nombre de la cookie:** el backend usa `session` si corre con `ENV=local` y `__Host-session` en cualquier otro caso (`Settings.session_cookie_name`). El frontend lo recibe en `SESSION_COOKIE_NAME` (obligatoria, ver "Variables de entorno"). No lo deduzcas de `NODE_ENV` ni de `VERCEL_ENV`: un `next start` o `vercel dev` con backend local no coinciden con el `ENV` del backend.
  - **401 en una página:** `redirect("/login")` fuera del `try` (`redirect` lanza). Si una página hace varias llamadas en paralelo, usa `Promise.allSettled` y deja que un 401 de cualquiera gane sobre otro fallo (sin 401, se informa el primer fallo en el orden de las llamadas), para que el resultado no dependa de cuál falla antes. En el log del servidor, de un error que no es `ApiError` solo va su nombre (`error.name`), nunca el mensaje: un error de parseo puede citar un trozo del cuerpo de la respuesta. El proxy (KAN-27) solo ve que hay cookie, no si es válida, así que esa comprobación se queda. Un Server Component no puede borrar la cookie vencida o revocada: por eso `/login` no redirige a `/` cuando hay cookie (habría un bucle `/` → 401 → `/login` → `/`). Usa `isUnauthorized(error)` (`lib/core/data/errors.ts`) en vez de repetir la comprobación. **401 en una query del navegador (KAN-59):** `makeQueryClient()` (`components/providers.tsx`) lleva un `QueryCache.onError` que, ante `isUnauthorized(error)`, hace `window.location.replace("/login")` (carga completa, como el logout). No actúa en el servidor ni si ya estás en `/login`, y redirige una sola vez aunque fallen varias queries. El `retry` por defecto no reintenta un 401 (sí el resto, hasta 3 veces). **No hay `MutationCache.onError` a propósito:** el canje de sesión del login es una mutación y su 401 (token inválido) debe verse en el formulario; si una mutación privada futura necesita el redirect, que lo haga ella.
- **Dinero:** llega como entero en la **unidad menor de la moneda** (ISO 4217): valor × 10^exponente, con el `exponent` que el API envía junto a `currency` (UYU 15,50 = `1550`; CLP 1.500 = `1500`). Nunca asumas ×100. Se formatea solo para mostrar, con `formatMoney(minor, { code, exponent }, { sign })` de `lib/core/money.ts`: locale fijo por moneda del espacio, solo para el dinero (`lib/core/locale.ts`: UYU y USD → es-UY, COP → es-CO, ARS → es-AR, BRL → pt-BR, EUR → es-ES; fallback es-UY; nunca el del dispositivo, y las fechas no lo leen: siguen en es-UY), **exactamente `exponent` decimales** y "−" tipográfico (U+2212) en negativos. Acepta `number` entero seguro, `bigint` o `string`; convierte con enteros y cadenas, nunca con `/ 100` ni floats. Sin aritmética con floats. Un monto escrito a mano se lee con `parseMoneyInput(text, exponent, { allowNegative })` y se muestra el símbolo con `currencySymbolOf` (campo: `MoneyField`, con `inputMode="decimal"`). **Separadores:** "," y "." son siempre el separador decimal y no existe separador de miles: "1.234" son tres decimales (error con exponente 0 o 2; con exponente 3 es 1,234), nunca 1234 (D11 y D18). El monto de un movimiento (`amount_minor` de gasto, ingreso o transferencia, siempre positivo) se valida con `moneyAmountSchema(exponent)` (`lib/core/schemas/money-input.ts`): texto → entero seguro mayor que 0; el cero lo rechaza el esquema y no el parser, porque un saldo o un cuadre sí pueden ser 0. El formulario entero de un movimiento es `movementFormSchema(exponent)` (`schemas/movement.ts`, KAN-94), que usa `moneyAmountSchema` para el monto.

Para que un esquema de request no se desvíe del contrato, comprueba que lo que infiere es asignable al tipo generado: `const _check: components["schemas"]["X"] = {} as z.input<typeof schema>` cuando el esquema **es** el cuerpo del request (sin `transform`). Si el formulario guarda texto y el esquema lo **transforma** en el cuerpo (el monto `"1550,50"` → `155050`, los días `"5"` → `5`: `accountFormSchema` de `schemas/account.ts`), lo asignable al tipo generado es la **salida**, y `z.input` es lo que guarda el formulario. Lo que de verdad lo sujeta es tipar con el tipo generado la función que arma el cuerpo (`const body: AccountCreate` en `buildAccountBody` y el retorno del `.transform`: un campo que el backend no tiene o de otro tipo rompe `typecheck` ahí); `const _check: AccountCreate = {} as z.output<ReturnType<typeof accountFormSchema>>` queda como segunda red por si alguien quita esas anotaciones. Si el esquema de formulario no se envía tal cual (el login), no lleva `_check`. Los chequeos entre campos (el saldo y los días dependen del tipo) van en un `.check()` del objeto, no en un `.transform()`: Zod no ejecuta el `transform` si un campo ya falló, y la persona vería los errores de a uno por intento. Cuando el cuerpo es una **unión por `type`** (`movementFormSchema`, KAN-94), el formulario es un objeto plano para no perder lo escrito al cambiar de tipo, la función que arma el cuerpo devuelve `{ ok, body } | { ok: false, issues }` (no hay cuerpo válido a medias) y el `loc` de un 422 trae el tipo entre `body` y el campo: `movementFormFieldOf` lo quita antes de buscar el campo.

## Variables de entorno
- **Validación:** `next.config.ts` llama `assertValidEnv()` (`lib/env/validate.ts`), así que `npm run dev` y `npm run build` fallan con un mensaje claro que lista **todas** las variables que faltan o están mal (servidor y cliente juntas). En local: `cp .env.example .env.local`.
- **Servidor:** `BACKEND_URL` (URL http(s), sin barra final) y `SESSION_COOKIE_NAME` (obligatoria: `session` o `__Host-session`, el nombre de la cookie que pone el backend; sin valor por defecto a propósito: olvidarla en staging dejaría a todos rebotando a `/login`; en Vercel va en Production y en Preview, KAN-14). Solo se leen desde `lib/env/server.ts` (`serverEnv`), que lleva `import "server-only"`: importarlo desde un componente cliente rompe el build.
- **Cliente:** `NEXT_PUBLIC_FIREBASE_API_KEY`, `NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN`, `NEXT_PUBLIC_FIREBASE_PROJECT_ID` (obligatorias) y `NEXT_PUBLIC_FIREBASE_AUTH_EMULATOR_HOST` (opcional, solo local). Se leen desde `lib/env/client.ts` (`clientEnv`). Son públicas: se incrustan en el bundle al hacer build, **nunca secretos**. Next solo las incrusta si se escriben como `process.env.NEXT_PUBLIC_X` literal (`client.ts` ya lo hace); no uses claves dinámicas ni pases `process.env` entero.
- **No leas `process.env` directamente** fuera de `lib/env/` (ESLint lo prohíbe): añade la variable al schema y léela vía `serverEnv` / `clientEnv`.
- **Emulador solo en local:** el build falla si `NEXT_PUBLIC_FIREBASE_AUTH_EMULATOR_HOST` está definida y existe `VERCEL_ENV` (misma regla que el backend). `vercel dev` también define `VERCEL_ENV=development`, así que la guarda impide usarlo con el emulador: en local usa `npm run dev`.
- Los schemas de servidor y cliente están en archivos separados a propósito: así el bundle del navegador no contiene los nombres de las variables de servidor.
- Lista comentada en `frontend/.env.example` (nunca leas `.env.local`). Cualquier variable nueva se añade a su schema **y** al `.env.example` en el mismo cambio.
